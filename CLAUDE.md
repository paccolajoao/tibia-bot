# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A Tibia pixel-bot: it **reads the screen** (computer vision), **decides**, and **simulates input** — no memory/packet injection. Ships with a live web dashboard. Windows-only.

> **Language convention:** the code, identifiers, comments, commit messages, and the README are all in **Brazilian Portuguese**. Match this — name new modules/classes/functions in Portuguese and keep comments in Portuguese. (e.g. `captura`=capture, `visao`=vision, `decisao`=decision, `entrada`=input, `nucleo`=core, `seguranca`=safety, `barramento`=event bus, `ponte`=bridge, `comportamento`=behavior, `alvo`=target, `saque`=loot, `cura`=heal.)

## Commands

All commands use the project venv interpreter directly (`.\.venv\Scripts\python.exe`). The shell is PowerShell.

```powershell
# Setup
py -3.13 -m venv .venv                                          # 3.12 or 3.13 both work
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt   # dev deps include pytest/ruff

# Portal frontend (Vite + React + Tailwind + shadcn). Build once; FastAPI serves portal/dist.
cd portal; npm install; npm run build; cd ..   # requires Node 18+
# (dev w/ hot-reload: cd portal; npm run dev  -> :5173, proxies /api and /ws to :8000)

# Run (prefer an Administrator terminal so SendInput reaches the elevated Tibia client)
.\.venv\Scripts\python.exe executar.py     # runs bot loop + portal at http://127.0.0.1:8000
#                                            (portal comes up even uncalibrated — calibrate in-browser)
.\.venv\Scripts\python.exe calibrar.py     # optional CLI calibration (writes the active SQLite profile)

# Tests (all offline — no game needed)
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pytest tests/test_motor_decisao.py -q          # single file
.\.venv\Scripts\python.exe -m pytest tests/test_alvo.py::test_nome -q        # single test

# Lint
.\.venv\Scripts\python.exe -m ruff check .
```

`pyproject.toml` sets `pythonpath = ["src", "."]` for pytest, so tests import `bot.*` without installing the package. The entrypoints (`executar.py`, `calibrar.py`) instead inject `src/` onto `sys.path` manually at startup.

## Architecture

**Two-thread model bridged by a queue.** This is the central design constraint:

```
THREAD DO BOT (synchronous)                    ASYNCIO (uvicorn / FastAPI)
captura -> visao -> decisao -> entrada    queue.Queue (bounded,    PonteAssincrona drains
        -> publica telemetria          ───  drop-oldest)  ──────►  the queue, broadcasts
                                                                    each event over WebSocket
control (pause/stop) panel -> bot: separate channel (ControladorExecucao: Lock + Event)
```

- [src/bot/nucleo/loop_bot.py](src/bot/nucleo/loop_bot.py) — `LoopBot(threading.Thread)`. The synchronous tick loop: capture → read bars → detect creatures → `motor.decidir` → execute input → publish telemetry. Steady cadence via `captura.fps_alvo`; the annotated preview and stats have their own throttles so they don't flood the WebSocket. `max_ticks` exists only for tests. **The whole tick body runs inside `_processar_tick`, wrapped in a try/except in `run()`** — any exception (detection/input/behavior) is logged (throttled) and swallowed so a single bad tick **never kills the bot thread**; `tick`/`max_ticks`/cadence run outside the try, so the loop keeps going (and still terminates under repeated errors).
- [src/bot/contexto.py](src/bot/contexto.py) — `Contexto`, the per-tick shared state. **Owned exclusively by the bot thread.** The dashboard never touches it — it only sees immutable telemetry snapshots. Preserving this ownership rule is what keeps the threading model simple; do not read/mutate `Contexto` from the async side.
- [src/bot/telemetria/barramento.py](src/bot/telemetria/barramento.py) — `BarramentoEventos`, the bounded queue. **Best-effort: drops the oldest event when full** so the bot loop never blocks on the panel. [ponte.py](src/bot/painel/ponte.py) adapts the blocking `queue.get()` to `await` via `run_in_executor`.

### Decision engine — the extension point

Behaviors are evaluated by **priority** (highest first); the **first non-null decision wins the tick** (one action per tick → human-like timing, no hotkey storms). Per-hotkey cooldowns gate actions. Action types (`TipoAcao` in [decisao/tipos.py](src/bot/decisao/tipos.py)): `PRESSIONAR_TECLA`, `CLICAR`, `CLICAR_DIREITO` (right-click at `Decisao.ponto` — cavebot uses it for ladders/levers), `ARRASTAR` (drag, for item drop — uses `Decisao.ponto`→`ponto_destino`), `NENHUMA`. A `CLICAR`/`CLICAR_DIREITO` decision with `dados["transformar"]=True` carries **frame/canvas** coords that the loop maps to desktop at runtime (OBS); behaviors whose points come from a detector (alvo/drop) are pre-transformed and omit the flag.

- [src/bot/decisao/comportamentos/base.py](src/bot/decisao/comportamentos/base.py) — `ComportamentoBase` protocol: a class with `nome`, `prioridade`, and `avaliar(contexto) -> Decisao | None`.
- [src/bot/decisao/motor.py](src/bot/decisao/motor.py) — `MotorDecisao` sorts behaviors by priority and returns the first triggered decision whose `chave_cd` is **off cooldown**. A triggered-but-on-cooldown decision does **not** stop the scan: it's recorded as the `NENHUMA`-with-reason fallback (surfaced in the panel) and the motor **continues to lower-priority behaviors** — so a blocked high-priority behavior still lets a lower one act this tick. The loop calls `confirmar_acao()` **after** executing to register the cooldown. This blocked-yields-to-lower cascade is what the healing camadas rely on to stack magia+poção across adjacent ticks.
- Current behaviors & default priorities: **healing camadas** `cura_forte` (106) > `pocao_vida` (104) > `cura_leve` (102) > `pocao_mana` (100) > `Saque` (~85) > `Alvo` (~80) > `MagiaAtaque` (~70) > `Drop` (~50) > `Cavebot` (~20) > `UsarMana` (~15) > `Comer` (~10). `Saque` sits above `Alvo` so Quick Loot fires right after a kill even with mobs still up. **`Alvo` does NOT gate attacking on `alvo_atual`** (the red-highlight detection conflates the target frame with a wounded creature's reddish HP bar — a false-positive there would stop the bot attacking, e.g. after killing one of several mobs or coming up stairs). Re-targeting is driven by `alvo_engajado_ts` (stamped by the loop on each attack) + battle-list **count drops** (kills via `saque_morte_ts`), with `recompromisso_s` as the missed-click safety net. **"Sem dano" watchdog** (`sem_dano_timeout_s`, default 10s, mirrors `Cavebot`'s combat watchdog below): the loop tracks the 1st battle-list entry's HP fill (`DeteccaoCriaturas.vida_primeira`, read the same way as the main HP/mana bars — see Vision) and stamps `alvo_dano_ts` in `estado_comportamentos` on a real drop; if `Alvo` stays engaged that long without `alvo_dano_ts`/`saque_morte_ts` advancing, it appends a **static** log suffix to `motivo` (dedupes to 1 line — see `_publicar_decisao`) instead of spamming every tick. Purely observability — it never changes which creature is attacked or the click cadence (`recompromisso_s` already covers re-clicking).
- **Auto-cura = 4 camadas** ([decisao/comportamentos/camada_cura.py](src/bot/decisao/comportamentos/camada_cura.py)): a single generic `CamadaCura` class instantiated 4× by `montar_camadas_cura(cura, confianca_minima)` (the **single source** of the layers + priorities, shared by `executar.py` and the tests; `cooldowns_cura(cura)` is the matching cooldown dict). Each camada = "quando a barra (HP|mana) ≤ limiar, aperte a tecla". The layers model Tibia's **cooldown groups**: the two potions (`pocao_vida`/`pocao_mana`) share the key `"grupo_pocao"` (`cd_pocao`) so **two potions never fire in the same turn**, while the spells (`cura_forte`/`cura_leve`) have their own keys, so a spell + a potion **do** fire on adjacent ticks (same ~1s turn) — the blocked-yields-to-lower cascade above is what produces the stacking. `pocao_mana` carries an HP-safety gate (`mana_hp_seguro`): it won't drink while confident HP ≤ that, reserving the shared potion cooldown for life. `cura_forte` is an emergency panic (long `cd_cura_forte`, default 120s). Stats: spells → `curas`/`curas_forte`/`curas_leve` (recurso `"hp"`), health potion → `pocoes_vida` (recurso `"pocao_vida"` — needs its own `elif`, or the `else` inflates `curas`), mana potion → `pocoes_mana` (recurso `"mana"`). A single `cura.ativo` toggles all four.
- **HP/Mana reads are stabilized between frames** ([visao/estabilizador.py](src/bot/visao/estabilizador.py), `EstabilizadorBarra`, applied by the loop right after `ler_percentual_barra`, gated by `visao.estabilizar_barras`): `barra_recursos._confianca` scores a **fully uniform** bar (all-empty/all-full — e.g. a bar occluded by an overlay) as confiança 1.0, so an occlusion could read as "HP 0% confiável" (panic-heal) or "HP 100% confiável" (suppress all healing). The estabilizador rejects a uniform 0%/100% that isn't corroborated by the previous frame AND coherent with the last good value (no impossible 30%→100% jump), and on rejected/low-confidence reads **holds the last good value** for a short TTL (pessimistic hold) so the cura doesn't go blind mid-burst.
- **Every behavior has an `ativo` flag in its config** (`cura.ativo`/`alvo.ativo` included — added so the portal's *Recursos* tab can toggle each feature). `executar.py` only registers the active ones; toggling here is the supported way to disable a feature (e.g. turn off `saque` on a premium account).
- `Cavebot` (navegação) walks the hunt by **clicking waypoints on the minimap** in sequence — Tibia pathfinds each leg; arrival at an `ir` waypoint is detected when the **minimap stops scrolling** (`visao/minimap.py` frame-diff, exposed by the loop as `minimap_movendo`/`minimap_score` in `estado_comportamentos`). The route loops circularly. Like `Alvo`, the loop stamps `cavebot_acao_ts` after executing so the state machine only "waits for arrival" once the click actually went out. Cooldown is keyed `"cavebot"`. Requires `regioes.minimap` calibrated + ≥1 waypoint.
  - **Yields to combat with a watchdog (anti-stuck):** it cedes while creatures are present, BUT if there's no kill for `combate_timeout_s` (default 15s; `0`=never give up) — e.g. an **unreachable mob** — it resumes walking instead of soft-locking forever (the `Alvo`/`MagiaAtaque` cooldowns leave gaps for it to step). This is the safety against "bot freezes attacking something it can't reach".
  - **Floor changes** are `andar_em` (left-click a tile), `usar` (right-click a ladder/lever), or `tecla` (rope/shovel hotkey) waypoints, with an optional `direcao` label (`subir`/`descer`, cosmetic — route clarity + logs, no mechanic change). A waypoint flagged `troca_andar=True` is **validated by a PERSISTENT minimap change, not a transient spike**: the loop snapshots the minimap crop right before the troca action executes (`_minimap_ref`, taken in the `cavebot_acao_ts` block when `dec.dados["troca_andar"]`) and each tick publishes `minimap_diff_ref` = diff of the current crop vs that reference (`visao/minimap.py:diferenca_minimapa`, shared with `minimapa_movendo`). The change is confirmed only when `minimap_diff_ref ≥ limiar_troca_andar` **AND** the minimap has settled (`minimap_movendo == False`) — so a respawn/teleport/combat spike that settles back to a similar map (diff_ref drops to ~0) does **not** falsely advance the waypoint. If not confirmed within `timeout_trecho_s` it **retries** the action up to `tentativas_troca` times, then advances best-effort (logs the retries via the decision `motivo`) — never hard-locks. `troca_andar=False` keeps the plain dwell. (`minimap_score` — instantaneous frame-to-frame diff — is still published for the `ir` arrival detection and debug.)
- `MagiaAtaque` presses **one** attack hotkey (`magia_ataque.tecla`) while the battle list shows creatures — the spell *rotation* is built inside the Tibia client on that hotkey. Respects a **mana floor** (`mana_minima`, default 30%) so it never drains the mana the healer needs. Priority below `Alvo`; cooldown keyed `"magia_ataque"` (= `intervalo_s`). Requires the battle list calibrated.
- `UsarMana` (Magic-Level training) casts `usar_mana.tecla` while mana ≥ `mana_alto`, with hysteresis down to `mana_alvo`. It's an **idle activity: it yields to combat** (returns nothing while the battle list shows creatures), so it never blocks attacking/looting regardless of its configured priority. **Gotcha:** a full bar rarely reads exactly `100%` (anti-aliased edges + overlaid digits → ~96–99%), so a configured `mana_alto >= 100` is treated as `LIMIAR_CHEIO_INATINGIVEL` (~97%); the default is `95` — set it at/below what a full bar actually reads (the *Usar Mana* tab shows the live mana to help). Its cooldown is keyed by `CHAVE_COOLDOWN` (`"usar_mana"`), not by the hotkey.

**To add a feature:** create a class implementing `ComportamentoBase` under [src/bot/decisao/comportamentos/](src/bot/decisao/comportamentos/), then register it in the `comportamentos` list in [executar.py](executar.py). Behaviors that need cross-tick state use `contexto.estado_comportamentos` (a namespaced scratch dict) — e.g. the loop stamps `saque_morte_ts` / `alvo_engajado_ts` there for `Saque`/`Alvo` to read. Other per-tick reads the loop computes and stores on `Contexto` directly: `criaturas` (battle list) and `itens_inventario` + `ponto_drop` (drop). Some cross-tick bookkeeping is done by the loop itself (e.g. `_rastrear_mortes` runs every tick because the motor short-circuits before low-priority behaviors run).

### Capture — pluggable backends with auto-fallback

[src/bot/captura/fabrica.py](src/bot/captura/fabrica.py) (`criar_capturador`) picks a backend. The rest of the bot only knows the `CapturadorBase` protocol ([base.py](src/bot/captura/base.py)), which returns a `Frame` (BGR `np.ndarray` + the absolute desktop `Regiao` it represents).

`backend: auto` tries **DXGI/bettercam** (Python <3.13 only) → **WGC** (Windows Graphics Capture; reads DX11/DX12/OpenGL, works on 3.13) → **mss** (pure-Python GDI; **cannot read GPU surfaces** — DX12 comes back black). Other backends: `obs` (OBS Virtual Camera, for the official BattlEye client), `tibia_arquivo` (slow screenshot-hotkey fallback). The loop also has a runtime safety net (`_verificar_frames_pretos`): if HP+Mana confidence stays ~0 for 30 ticks it auto-switches to mss (or, on OBS, just warns).

**Black-capture is the #1 operational gotcha.** The official Tibia client (BattlEye) uses `WDA_EXCLUDEFROMCAPTURE`, which makes the Windows compositor blank the window for *every* external capture path → use `backend: obs`. See the README's OBS section for the full setup.

### Entrada — pluggable backends (SendInput vs. Arduino HID)

[src/bot/entrada/fabrica.py](src/bot/entrada/fabrica.py) (`criar_entrada`) mirrors the capture factory: the rest of the bot only knows the `EntradaBase` protocol ([base.py](src/bot/entrada/base.py), 4 methods — `pressionar_tecla`/`clicar`/`clicar_direito`/`arrastar`), a `Protocol` matched structurally, never subclassed. Unlike capture there's no `auto` — `entrada.backend` is explicit (`directinput` default | `arduino`), and a non-default backend that fails to init **raises** (no silent fallback: if the user picked Arduino, usually for elevation/anti-detection reasons, silently falling back to SendInput would defeat the point).

- `directinput` (default, [teclado_directinput.py](src/bot/entrada/teclado_directinput.py)) — `EntradaDirectInput` wraps `pydirectinput` (Win32 `SendInput`).
- `arduino` ([teclado_arduino.py](src/bot/entrada/teclado_arduino.py)) — `EntradaArduino` talks a line-based serial protocol (`K <tecla>` / `M <hx> <hy>` / `MR <hx> <hy>` / `D <hx1> <hy1> <hx2> <hy2>`, plus diagnostic-only `P` and `MV <hx> <hy>`, `OK`/`ERR ...` replies) to a **separate HID-capable board** (ATmega32u4 — Arduino Leonardo/Micro/Pro Micro), running the reference firmware [arduino/entrada_hid/entrada_hid.ino](arduino/entrada_hid/entrada_hid.ino) (HID-Project's `BootKeyboard` + `AbsoluteMouse`). **Not the RoboCore BlackBoard** — it's an ATmega328P Uno-clone with a fixed USB-serial bridge chip, no native USB, structurally unable to enumerate as HID under any firmware. Python pre-scales pixel coords to the HID absolute range (0–32767) before sending — the firmware keeps no resolution state. **Known limitation:** Windows' absolute-HID-pointer driver only reaches the **primary monitor**; Tibia must run there for `arduino` mouse clicks to land correctly (see [arduino/README.md](arduino/README.md)).
- Both backends accept the same `atraso_pre_ms`/`atraso_pos_ms` jitter tuples (`entrada/atrasos.py:atraso_humano`) around each action, so timing behavior is consistent regardless of backend.
- **Portal → Configurações → Arduino** (dedicated tab, separate from Sistema) has a status checklist (backend=arduino? port filled? port currently detected via `serial.tools.list_ports`, surfaced in `/api/meta`'s `portas_seriais`), the config fields, and a **live hardware test** (`POST /api/entrada/arduino/testar` → `entrada/teclado_arduino.py:executar_diagnostico`) that opens its own short-lived serial connection (independent of the bot's — fails loudly with a clear message if the bot is already running `backend: arduino` and holding the port) and runs, per-step, non-aborting: `conectar` → `ping` (new `P`/`PONG` wire command, touches neither keyboard nor mouse) → `teclado` (presses `CAPSLOCK` — reversible, no text typed, nothing clicked) → `mouse_movimento` (new `MV`, moves the cursor only) → optionally `mouse_clique` (a real click, **opt-in**, requires an explicit coordinate from the UI — the one step with real side effects, since it interacts with whatever is under the cursor). Each step reports its own round-trip latency in ms. The test payload is whatever's currently typed in the form — no need to hit Salvar first (saving is still the unchanged whole-`Config` `PUT /api/config`).
- A second, independent delay layer — `atraso_reacao_ms`/`atraso_reacao_critico_ms` — models human *reaction* time (vs. the pre/post jitter's *motor* micro-tremor). It's applied **once per dispatched decision**, in [loop_bot.py](src/bot/nucleo/loop_bot.py) right after `motor.decidir` (not inside the entrada backend, since it needs `dec.dados`), gated on `janela_focada` and `acao != NENHUMA` so idle ticks never sleep for nothing. `eh_cura_critica`/`faixa_atraso_reacao` (`entrada/atrasos.py`) exempt `cura_forte`/`pocao_vida` (the two highest-priority healing camadas — see [camada_cura.py](src/bot/decisao/comportamentos/camada_cura.py)) from the full delay, since a blocking sleep before an HP panic-heal also delays the next tick's HP read. **Both ranges default to `(0, 0)` (off)** — deliberately, so `EntradaSimulada`-backed loop-integration tests stay fast/deterministic; set them (e.g. `100–1500ms` / `0–50ms`) via the portal's Sistema tab to opt in.

### Vision

- [src/bot/visao/barra_recursos.py](src/bot/visao/barra_recursos.py) — reads bar fill % by classifying **per-column over the full bar height** (not a single mid scanline) in **HSV (brightness + saturation)**, so it survives HP changing color **and the digits overlaid on the bar** (`165/170` — white text is low-saturation, but the bar color above/below the digit keeps the column "filled"; a column counts as filled if ≥`FRACAO_COLUNA` of it is filled). Takes `invertido` for bars that fill **right→left** (Tibia mana empties left→right) — it mirrors the column array before the same contiguous-from-edge logic. Occluded/dirty reads (tooltip covering the bar) yield **low confidence** and are ignored downstream (`visao.confianca_minima`).
- [src/bot/visao/lista_batalha.py](src/bot/visao/lista_batalha.py) — detects creatures in the battle list (mini HP-bars) and whether there's a current target; provides the click point for targeting. Also reads the **fill % of just the 1st (topmost) entry** (`vida_primeira`, reusing `barra_recursos`'s column-classification helper on the already-computed saturation mask — no per-creature tracking beyond that one slot) for `Alvo`'s "sem dano" watchdog.
- [src/bot/visao/inventario.py](src/bot/visao/inventario.py) — `detectar_itens` finds registered items in the backpack region via **multi-scale template matching** (`cv2.matchTemplate`, TM_CCOEFF_NORMED, swept over `ESCALAS` ≈ 0.5×–1.5× → robust to client-zoom / icon-size mismatch). Templates are item-icon crops **or uploaded PNG/GIF files** registered in the portal; `decodificar_template` keeps the alpha channel (`IMREAD_UNCHANGED`) and `_normalizar_template` turns it into a **match mask** so transparent backgrounds of external/wiki icons are ignored. Used by the `Drop` behavior.
- [src/bot/visao/minimap.py](src/bot/visao/minimap.py) — `minimapa_movendo` compares two consecutive minimap crops (cv2.absdiff mean, **masking the central player marker**) and returns whether the minimap is **scrolling** (player walking). It detects **motion, not position** — that's all the `Cavebot` needs to know it arrived (minimap stops). The loop captures the `minimap` region per-tick (like battle_list/inventory) in `_detectar_minimap`.

### OBS coordinate mapping

With `backend: obs`, calibrated regions are in **OBS canvas coordinates**. The targeting click is converted to desktop coordinates at runtime by reading the **live Tibia window client rect** ([src/bot/captura/mapeamento.py](src/bot/captura/mapeamento.py)), so moving the window doesn't require recalibration. See `_configurar_mapeamento_obs` in [loop_bot.py](src/bot/nucleo/loop_bot.py).

### Config, persistence & the portal

- [src/bot/configuracao.py](src/bot/configuracao.py) — pydantic `Config` models. Still the **in-memory single source of truth** (nothing hardcodes coordinates), but no longer loaded from YAML at runtime.
- [src/bot/persistencia/](src/bot/persistencia/) — **config now lives in SQLite** (`config/bot.db`). `repo_perfis.py` does CRUD over **profiles**; each profile stores a whole `Config` as a JSON blob, exactly one is `ativo`. On first run the DB is seeded from the existing `config.yaml` (transparent migration). `executar.py`/`calibrar.py` read/write the **active profile**. YAML survives only as seed + import/export. `Config` (de)serialization helpers: `config_para_dict`/`config_de_dict`.
- [src/bot/painel/api.py](src/bot/painel/api.py) — REST API under `/api` (profiles, config, regions, YAML import/export, one-shot calibration frame via [captura/instantaneo.py](src/bot/captura/instantaneo.py)). [servidor.py](src/bot/painel/servidor.py) mounts it, keeps the `/ws` telemetry/control channel, and serves `portal/dist` (SPA) when built, else the legacy vanilla panel.
- [portal/](portal/) — the web portal (Vite + React + TS + Tailwind v4 + shadcn-style Radix primitives). Pages: Dashboard (live WS; stats incl. abates/curas forte-leve/usos de mana + per-minute rates), Configurações (a **Recursos** tab toggles each feature on/off with dependency hints + "em teste" badges, plus per-section forms; the **Drop** tab registers items by cropping a captured frame **or uploading a PNG/GIF** → PNG base64; the **Cavebot** tab records an ordered waypoint route by clicking points on a captured frame — minimap point for `ir`, game-world point for `andar_em`/`usar`, plus a *muda de andar (validar)* toggle and a *Direção* (subir/descer, cosmetic label) select for floor-change waypoints — with reorder/remove; the **Magia de ataque** tab sets the single attack hotkey + mana floor), Perfis (profiles + import/export), Calibração (draw HP/Mana/battle-list/**inventário**/**drop_tile**/**minimap** rectangles on a captured frame). **TS types in `portal/src/lib/types.ts` mirror the pydantic `Config` (and the telemetry events) — update both sides when adding a field.**
- **Applying config changes requires a bot restart** (deliberate: simpler than live reconfiguration). The portal saves to SQLite; changes take effect on the next `executar.py`. The portal stays up even when uncalibrated so you can calibrate/configure first.
- [src/bot/nucleo/seguranca.py](src/bot/nucleo/seguranca.py) — global hotkeys **F11** (pause/resume) / **F12** (panic, stops input immediately), plus window-focus gating. Focus gates **only the input** (SendInput needs the window focused), not the reading — the panel keeps showing live HP/Mana even when Tibia isn't focused.

## Notes

- Hotkeys must be bound **inside the Tibia client** to match the active profile's config (the bot only presses keys). Auto-loot relies on Tibia's **Quick Loot** + the client's own loot lists — item filtering is not managed by the bot.
- Session stats live in [src/bot/telemetria/estatisticas.py](src/bot/telemetria/estatisticas.py): `registrar_acao` buckets each executed action by `decisao.dados['recurso']` (`hp`→`curas`, split `curas_forte`/`curas_leve` by `dados['nivel']`; `pocao_vida`→`pocoes_vida`; `mana`→`pocoes_mana`; `mana_uso`→`usos_mana`; `alvo`→`ataques`; `saque`→`saques`; `comida`→`refeicoes`; `cavebot`→`passos_cavebot`; `magia_ataque`→`magias_ataque`), and `_rastrear_mortes` bumps `abates` when the battle-list count drops. **Gotcha:** the `else` of `registrar_acao` falls into `hp`/`curas`, so any new `recurso` MUST get an explicit `elif` (else it inflates the cure count). These count **what the bot did (inputs sent)**, not client-confirmed events — surfaced as such in the dashboard.
- Every behavior is gated by an `ativo` flag (`cura`/`alvo` included). `targeting`/`auto-loot` additionally require the **battle list region calibrated**. **Drop** activates only when `drop.ativo` + `regioes.inventario`/`drop_tile` calibrated + at least one item registered; it drags items to the ground tile (and presses Enter for the stackable "Move how many?" dialog if `confirmar_quantidade`). **Cavebot** activates only when `cavebot.ativo` + `regioes.minimap` calibrated + at least one waypoint; it clicks minimap waypoints to walk and yields to combat.
- Run as Administrator: required for global hotkeys and for SendInput to reach the (usually elevated) Tibia client.
